## 1. 系统概述

> **产品定位（能力边界，非谦辞）**：最终产出**决策预演报告** —— 不是研究结论，而是把多方视角、信息盲区与分歧摆到桌面上，供决策者在投入资源前自检。**产品定位是预演工具而非研究工具。**
>
> 技术含义：讨论由 6 个 AI 角色生成，**不是学术判断**；文献仅作背景注入，标「待验证」的内容需使用者自行核实；评审为 AI 独立评审、无人类盲评。界面上每次结果顶部有定位声明、底部有引用纪律。详见《作品申报书》「产品定位」一节。


群智基于 v14 科研协作预演沙盘（**566 轮评审记录版**）产品化改造，新增**多源学术检索装置**（11 源 + 五道质量闸门 + 期刊分级）、主教练联网搜索、课题复杂度分级、讨论前认知锚点、预设教研课题库、场景化决策报告与反馈闭环，形成统一的 FastAPI 参赛版。它不只是本地 Demo：已**云端 7×24 常驻**（腾讯云，systemd 托管），新功能先在与线上隔离的**体验版**验证后才上线（见第 3 节）。

| 项 | 数字 | 项 | 数字 |
|---|---|---|---|
| 认知原型 / 价值观取向 | **7 / 6** | 专业领域 / 团队人数 | **8**（选 6 人）/ **6** |
| 干预指令 / 复杂度分级 | **8 类 / 3 档** | 讨论轮数 | **1–4 轮** |
| **理论组合空间** | **336 = 7 × 8 × 6**（不是实验结论、不作优势）| 人格维度效应 | 最优 vs 默认 **d≈0.05**（可忽略；⚠ 该值来自已作废评审库，不作结论）；有实证支撑的是**成员之间应当有差异（覆盖维度上有数据支持）**（−1.05，p=0.0012，dz=−0.99）|

## 2. 环境要求

- **运行 / 部署环境**：Python **3.10+**（开发环境 3.13）；fastapi, uvicorn, pydantic, requests, chromadb, rank-bm25, jieba, sentence-transformers（见 `requirements.txt`）；Linux（实机腾讯云轻量 **2 核 4G**）、systemd、git、**Node.js**（前端守卫）、nginx。
- **模型调用**：**requests 直连（硬超时），不用 OpenAI SDK**（避免 SDK ssl 无限阻塞）；DeepSeek 必填（`DEEPSEEK_API_KEY`）；Qwen（人话化）/GLM（深批者、v3 评审）可选、未配置回落 DeepSeek；博查 `BOCHA_API_KEY`（联网兜底）。**多源学术检索不需要任何额外模型或 Key**（仅 `requests`）；本地向量知识库为可选组件，若启用才需 bge-small-zh-v1.5 + bge-reranker-base（`app/rag/models/`，约 1.2 GB），**默认不部署**。

## 3. 云端部署与线上运行

> 这一节回答一件事：**这套东西现在就在公网上跑着。**

### 3.1 真实运行事实

| 项目 | 取值 |
|---|---|
| 服务器 / 托管 | 腾讯云轻量应用服务器（2 核 4G），**7×24 常驻**；systemd `Restart=always` + `RestartSec=5` + 开机自启；健康检查 `GET /health` 返回 200，应急 `sudo systemctl restart qunzhi-gateway qunzhi-a2a` |
| 网页版 | `http://134.175.145.241:5020/?key=<口令>`（口令由环境变量 `QUNZHI_ACCESS_KEY` 提供）|
| A2A 接口 | `http://134.175.145.241:5080/`，**供其他智能体/平台按标准协议调用**（平台只填 SSE URL、自动解析 Agent Card，**平台侧无需密钥**）；A2A 1.0（JSON-RPC 2.0），支持 `message/send`、`message/stream`、`get_task` |

### 3.2 服务清单与角色

| 服务 | 端口 | 单元 | 角色 |
|---|---|---|---|
| 网关 | 5020 | `qunzhi-gateway` | 线上主服务：控制台、启动预演、SSE 讨论流、结果查询 |
| A2A | 5080 | `qunzhi-a2a` | 智能体对智能体：收问题 → 跑一轮预演 → 返回《决策建议书》|
| 体验版 | 127.0.0.1:**5021** | `qunzhi-staging` | 隔离环境，**只监听回环**，由 nginx 以 `/staging/` 对外 |
| nginx | 3081 | `nginx` | `/staging/` → 5021 反代；另承载问卷/盲评等辅助页面 |

顺序：`qunzhi-a2a` 先起，`qunzhi-gateway` 依赖它。

### 3.3 双环境隔离

| 维度 | 线上环境 | 体验版 |
|---|---|---|
| 目录 / 分支 | `/home/ubuntu/qunzhi`，`main`（稳定版）| `/home/ubuntu/qunzhi-staging`，`v6-plugin-experiment` |
| 进程 / 数据 | `qunzhi-gateway`（5020），`data/sessions/` | `qunzhi-staging`（127.0.0.1:5021），独立目录 → **数据天然独立** |
| 访问 / 用途 | `:5020/?key=...`，用户日常使用 | `:3081/staging/?key=...`，新功能先验证、通过才上线 |

**为什么必须两套**：新功能直接上线会打断正在使用的人的流程——这是**真实踩过的教训**；隔离后体验版改坏了，线上**一行都不动**（体验版只监听回环，靠 nginx 反代对外）。

### 3.4 部署流水线（可复现的工程过程）

```bash
# 统一入口 deploy_版本化.py；-m 为改动说明（进 git 提交信息），其后为要部署的文件
python deploy_版本化.py -m "修复前端 SSE 重连" app/main_gateway.py app/templates/console_new.html
```

| 步骤 | 动作 | 不通过怎么办 |
|---|---|---|
| ① 上传 | SFTP 覆盖远端文件 | 本地缺文件 → **中止** |
| ② **逐文件 sha256 校验** | 本地哈希 vs 远端 `sha256sum` | 任一不一致 → **中止** |
| ③ 远端 `py_compile` | `venv/bin/python -m py_compile <改动的 .py>` | 编译不过 → **中止** |
| ③b **前端 JS 真解析** | 抽出页面 `<script>` 交给 `node --check` | 语法错误 → **中止** |
| ④ 全量自测 | 远端 `_selftest_*.py` 全跑 | 任一失败 → **不提交、不重启** |
| ⑤–⑦ | `git commit` → `systemctl restart` 两服务 → `curl /health` | — |

**任一守卫不过，就在提交与重启之前停住**——不带着坏代码往下走。

**为什么加 ③b 这道 JS 真解析守卫**：曾用脚本替换页面的 `connectStream` 时多留一个花括号，页面 **HTTP 200 能正常打开、但脚本语法错误、所有按钮失灵**，用户报的是"**服务器崩了**"——其实是前端挂了，而当时只判断"字符串在不在"、**没有真正解析**。此后有 `.html` 改动就必须过 `node --check`，**不过则中止**：**用"数括号"防不住**。

### 3.5 版本化与回滚

每次部署自动 `git commit`（提交信息即改动说明，结束打印 commit 短哈希），线上与体验版各有分支。回滚**一条命令**：

```bash
cd /home/ubuntu/qunzhi && git revert HEAD --no-edit && sudo systemctl restart qunzhi-gateway qunzhi-a2a
```

### 3.6 稳定性机制

**四道熔断——任何环节都不会无限等待**

| 熔断 | 上限 | 到点行为 |
|---|---|---|
| 单次模型调用 | **90 秒** | 该次调用放弃，记失败 |
| v6 评审整体 | **240 秒** | 不再发新调用，**不展示任何分数**，如实标注"超时未执行" |
| 后处理合计（人话化/v3/深批者）| **240 秒** | 放弃等待，已产出部分照常返回 |
| 深批者 | **90 秒** | 本局不展示深批者，其余结果不受影响 |

**设计原则：任何环节都不会无限等待；到点用已有结果返回，缺哪个模块如实标注**。**讨论记录可重放**：讨论与会话全文落盘 `data/sessions/`，**刷新/服务重启/换设备都能完整回放**；评审算完**立即补存一次**，避免落盘缺字段。

### 3.7 成本（实测，非估算）

| 场景 | 调用 | token | 成本 | 耗时 |
|---|---|---|---|---|
| 完整预演 | 37 次 | 47,261 | **¥0.16** | ~110 秒 |
| 快速预演 | 7 次 | 7,571 | **¥0.03** | ~27 秒 |
| 6 人团队 vs 单模型 | — | 45,074 / 2,437 | —（token 比 18.5 倍，非成本） | — |

一次完整预演约**一毛六**：主动选"多轮小调用"而非"单次超长调用"，换来**可控的超时与重试边界**。

### 3.8 数据合规与真实性边界

- **数据流向**：课题与想法随调用发给第三方模型 API（DeepSeek），**不落第三方存储**；会话记录存本地 `data/sessions/` 用于复盘，**不采集个人身份信息**。
- **真实性边界**：**"7×24 常驻"指服务可用性，不代表已有真实用户量**——除团队自测与演示案例外，**尚无外部用户规模数据**，不在这一点上提前许诺。

## 4. 部署步骤（本地 / 云端通用）

```bash
# 本地
cd 群智_提交版 && pip install -r requirements.txt
cp .env.example .env && python app/main_gateway.py     # 填 Key；口令用环境变量 QUNZHI_ACCESS_KEY 设置

# 云服务器（Linux）
mkdir -p /home/ubuntu/qunzhi && cd /home/ubuntu/qunzhi
python3 -m venv venv && venv/bin/pip install -U pip && venv/bin/pip install -r requirements.txt
git clone <仓库> . && cp .env.example .env && vi .env    # 同步代码（不含 data/）+ 填 Key
sudo systemctl daemon-reload && sudo systemctl enable --now qunzhi-a2a qunzhi-gateway
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5020/health    # 应为 200
sudo ufw allow 5020/tcp && sudo ufw allow 5080/tcp     # 腾讯云控制台「安全组」同样放行
nginx -t && sudo systemctl reload nginx                # 改完 nginx 配置先测语法再 reload
```

体验版**无需放行端口**（只监听 `127.0.0.1:5021`，靠 nginx 反代）；正式常驻一律用 systemd，不用 nohup。

**systemd 单元示例**（`/etc/systemd/system/qunzhi-gateway.service`）

```ini
[Unit]
Description=QunZhi Full Gateway
After=network.target qunzhi-a2a.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/qunzhi/app
ExecStart=/home/ubuntu/qunzhi/venv/bin/python /home/ubuntu/qunzhi/app/main_gateway.py
Restart=always
RestartSec=5
Environment=PYTHONUNBUFFERED=1

[Install]
WantedBy=multi-user.target
```

- `qunzhi-a2a.service`：同结构，改 `After=network.target` 与 `ExecStart=.../a2a_server.py`。
- `qunzhi-staging.service`：同结构，加 `Environment=QZ_PORT=5021` 与 `EnvironmentFile=/home/ubuntu/qunzhi/.env`，`ExecStart` 指向 staging 目录；nginx `/staging/` 用 `proxy_pass http://127.0.0.1:5021/;` + `proxy_buffering off;` + `proxy_read_timeout 3600s;`。

## 5. 模块说明

- **网关 `main_gateway.py`（5020）**：控制台、启动预演、SSE 讨论流、结果查询、主教练搜索/对话、预设课题库、插件清单、反馈闭环（端点见第 6 节）。
- **主教练 `coach_search.py`**：博查 Web Search API；查询改写 → 多角度搜索 → 净化 → **不对称注入**（每人不同切片）；XML 标签隔离、零宽字符清洗、可疑指令拦截、来源标注。
- **多源学术检索 `rag/`**：11 个检索源（10 学术库 + 1 联网搜索）并发检索 + 五道质量闸门 + 期刊分级（CSSCI/北大核心/SJR）+ 逐源台账；按课题类型自动路由来源（中/英、社科/医健/理工），**缓存优先**、带来源标注。本地向量知识库（Chroma + BM25 + RRF + bge 重排）为**可选组件，默认不部署**。
- **分级 / 课题库 / 报告**：`complexity.py` 自动分级（3 档、4 个通用维度），差异化配置轮数（1–4）、检索量、干预强度；`presets.py` 含 8 个教研课题，教研场景输出《教研决策建议书》（6 板块含认知盲区）+ 人话报告。
- **讨论引擎 `sandbox/app.py`**：三层人格 × 8 专业可选 × 6 人 × 信息不对称；讨论前认知锚点（每人 1 轮，V15.3）；Coach 审计 + 8 类干预。
- **保护与对接**：`guard.py` 做 `ACCESS_KEY` 校验（`?key=`）+ IP 限流（60s/3 次启动、10s/20 请求）；`a2a_server.py` 在 5080 提供 A2A 1.0 + SSE，以 `artifact` 返回《决策建议书》全文。

### 5.1 多源学术检索（11 个检索源插件）

每源一个独立文件，自带 `order`（优先级）与 `applies_when`（适用条件）。**默认启用 5 个**：`ncpssd`（中文社科，限中文词）、`chinaxiv`（中英文预印本）、`nstl`（中文科技期刊）、`crossref`（全学科期刊会议）、`doaj`（开放获取期刊）；**按需启用 6 个**：`cnki` 知网（需 `cookies/cnki.json`）、`pubmed`（医学课题且用英文检索式）、`semanticscholar`、`openalex`（全球文献 2.5 亿+）、`arxiv`、`bocha` 博查 Web（需 `BOCHA_API_KEY`）——除知网与博查外，其余 **9 个均免 Key**。

**五道质量闸门**（每条注入玩家的信息都要过）：① **低质源过滤**——30+ 文库/资料站、作业题页、`.docx` 文件名特征、灌水与广告页；② **学术时效过滤**——学术类只收近 **3 年**，不足放宽至 5 年，仍不足则用较早文献补位并**显式标注"较早文献，仅作背景参考"**；③ **国际源相关性裁判**——词面重合会误判（"液压电梯低温适应性" vs "低温锂电池 SOC"），对国际源候选做一次 LLM 裁判，剔除研究对象不同的；④ **注入上限与排序**——学术来源优先，最终注入 **≤8 条**；⑤ **完整性过滤**——出版类型判定 + 撤稿一票否决 + 网络来源白名单。（注：以上为**前置过滤**；注入前的 `quality_gate` 另有五步：去重与版本合并 → 每来源配额 → 期刊分级 → 排序并剔除「三无」→ 完整性+白名单。）

### 5.2 插件化架构（V16.2 → V16.3）

**统一契约**：插件是独立文件，自带 `PLUGIN` 元数据（id/kind/耗时/免 Key/优先级/适用条件）+ `available()` + `run()`/`search()`；**加同类插件 = 丢一个文件**，调度层一行不用改，由 `app/plugin_registry.py` 按 `KINDS` 调度。

| 类别 | 目录 | 数量 | 用户可见性 |
|---|---|---|---|
| 评审器 `review` | `app/review_plugins/` | 2 个（v3/v6），**用户自选** | `GET /api/review/plugins` 列耗时与成本，由用户权衡"快"与"准" |
| 检索源 `source` | `app/source_plugins/` | **11 个**（见 5.1）| `GET /api/plugins/sources` 列本局实际会跑的源与顺序 |

刻意的设计选择：**即插即用，但不偷偷换人**（插件不可用就如实记"不可用"，**绝不悄悄回落**）；**旧端点逐字保留**（`/api/review/evaluate`、`/api/review/v6`）；**默认评审器一键切换**（`QZ_DEFAULT_REVIEW_PLUGIN=v3|v6`）。

### 5.3 v6 评审模块（`review_v6.py`）

| 机制 | 做法 |
|---|---|
| **成对强制选择** | 不再给 1–10 分，改为两份材料**二选一**——猜中率 50%、**能失败**的检验 |
| **分维三档** | 各维度按"强 / 中 / 弱 / 无依据"判定，**不求和、不凑总分** |
| **锚点自检** | 先跑已知答案的锚点题（甲：完整版应胜出；乙：应判平局）；**未过则不出分** |
| **独立风险栏 / 超时不出分** | 风险条目与评分分开；达 240 秒整体截止即停，如实标注"超时未执行" |

**为什么把 1–10 分下线**：v3 的 1–10 分尺子在同一批 **18 对**材料上**只挑对 8/18（44%）**——**低于瞎猜的 50%**，根因是**尺子没有刻度**（分数挤在 6.4–7.2、门槛 0.5）。处置：1–10 分下线、改用 v6 成对强制选择，旧尺子留档并标注证伪数据；v6 验证三家评审 **18/18、17/18、17/18** 全部达标且**两轮一致**。耗时：v3 约 **40 秒** / v6 约 **160 秒**（v6 含锚点自检 + 三模型分维，故**单独开线程、不占报告链路**，见第 8 节）。

## 6. 核心接口文档

```
POST http://<IP>:5020/api/sandbox/start?key=<口令>
{ "topic": "<课题>", "user_thought": "<你的想法>", "max_rounds": 3,
  "info_mode": "coach_search", "scenario": "教研", "review_plugin": "v6" }   // v3 约 40 秒 / v6 约 160 秒
GET  http://<IP>:5020/api/sandbox/result/{session_id}?key=<口令>   # 报告/涌现/评估/审计/场景化报告/v6 评审
GET  http://<IP>:5020/api/plugins?kind=source&key=<口令>           # 检索源插件；/api/review/plugins 评审器
POST http://<IP>:5020/api/review/run/{plugin_id}?key=<口令>        # 按 id 跑评审
```

## 7. 数据流

```
用户输入课题 + 想法 → 复杂度分级（3 档）
  → 多源学术检索（11 个检索源插件）+ 联网搜索（博查）→ 五道质量闸门 → 净化 → 不对称注入 6 名玩家
  → 组建 6 人多学科团队（三层人格 × 8 专业）→ 认知锚点：每人 1 轮自我讨论（V15.3）
  → 多轮结构化讨论（1–4 轮；主教练审计 + 8 类干预）
  ├─ 报告链路（先出）：报告 → 人话化 → v3 评审 → 深批者
  └─ 评审线程（并行、后到）：用户所选评审插件（v3 约 40 秒 / v6 约 160 秒）
  → 场景化报告（教研建议书 + 认知盲区）→ 会话落盘可重放 → 反馈闭环
```

| 场景 | 耗时 |
|---|---|
| 简单课题（1 轮快速讨论，比赛演示模式）| 约 60–90 秒 |
| 中等/复杂课题（3 轮讨论 + 报告 + 评审）| **2–4 分钟**（130–240 秒，含认知锚点 1 轮）|
| 选 v6 评审 | 报告先出，**再等约 2–3 分钟**（实测约 160 秒）|

**报告与评审并行执行，评审在独立线程**：报告链路先走完，用户**先拿到报告**；评审独立线程跑（v6 约 160 秒）——塞进报告那条串行链会把"人话报告"一起拖慢。两边各有截止时间（见 3.6），到点用已有结果返回、缺哪个模块如实标注，评审算完**立刻补存一次**。

## 10. 安全与合规

| 项 | 处置 |
|---|---|
| 密钥 / 访问保护 | 提交版**不含任何 API 密钥**（经 `.env`）；`ACCESS_KEY`（由环境变量 `QUNZHI_ACCESS_KEY` 提供）+ IP 级限流；公网仅开放 5020（需口令）与 5080（A2A，开放调用 + IP 限流），体验版 5021 只监听回环 |
