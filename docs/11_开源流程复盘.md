## 阶段 2：安全扫描

### 做了什么

写脚本扫 168 个文件，找这些模式：

```python
PATTERNS = [
    ("API 密钥",      r"\bsk-[A-Za-z0-9]{16,}"),
    ("GitHub token",  r"\bghp_[A-Za-z0-9]{30,}"),
    ("学号",          r"\b(250223101212|2\d{11})\b"),
    ("手机号",        r"\b1[3-9]\d{9}\b"),
    ("真实姓名",      r"付云峰"),
    ("学校名",        r"长江师范学院"),
    ("服务器 IP",     r"\b134\.175\.145\.241\b"),
    ("访问口令",      r"qunzhi2026"),
]
```

### 结果

| 项 | 结果 |
|---|---|
| API 密钥 | ✅ **0 处** |
| GitHub token | ✅ 0 处 |
| 学号 | ✅ **0 处** |
| 手机号 | ✅ 0 处 |
| 真实姓名 | ✅ **0 处** |
| 学校名 | ✅ **0 处** |
| 本机路径 | ✅ 0 处 |
| **访问口令 `qunzhi2026`** | ❌ **8 处** |
| 服务器 IP | ⚠️ 6 处（决定保留）|

**长十六进制 16 处** —— 查证后是数据文件的 SHA256 校验值，无害。
**邮箱 8 处** —— 全是 `example.com` 占位符，无害。

### 关键判断

**`qunzhi2026` 必须换掉** —— 它出现在：
```
docs/02_作品文档.md
docs/04_开发说明.md
journey/02_变更记录.md
src/app/guard.py          ← 代码里硬编码
src/app/test_v6_code.py
src/app/templates/console_new.html
```

**改法：改成环境变量**
```python
# 之前
ACCESS_KEY = "qunzhi2026"

# 之后
ACCESS_KEY = os.environ.get("QUNZHI_ACCESS_KEY", "CHANGE_ME_ACCESS_KEY")
```

**服务器 IP 决定保留** —— 这是作者主动公开的演示站，要给人试。

### 教训

> **扫出来的结果要分三类看：**
> **① 真危险（密钥/口令）→ 必须改**
> **② 有意保留（演示站 IP）→ 写清楚为什么保留**
> **③ 误报（哈希/占位符）→ 记录判定依据，别直接忽略**

## 阶段 3：脱敏

### 做了什么

把 6 个文件里的 `qunzhi2026` 全部替换成环境变量读取。

### 验证方式

```powershell
# 全仓再扫一遍，确认 0 残留
Select-String -Path (Get-ChildItem -Recurse -Include *.md,*.py,*.html) `
              -Pattern "qunzhi2026"
```

### 顺手发现的问题

**改完部署到服务器时踩了坑**：新代码读环境变量，但服务器没配 → **API 全部 401**。

**修法：给 systemd 加 Drop-in**
```ini
# /etc/systemd/system/qunzhi-gateway.service.d/budget.conf
[Service]
Environment=QUNZHI_ACCESS_KEY=qunzhi2026
Environment=QUNZHI_DAILY_BUDGET=50
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart qunzhi-gateway
```

### 教训

> **脱敏不能只改仓库。**
> **线上服务如果也用了这个值，改完必须同步配环境变量，否则服务立刻挂。**

## 阶段 5：重写文档

### 为什么重写

原 README 是给**评委**看的，不是给**陌生人**看的。

**最致命的一句**（在旧 README 第 15 行）：

```markdown
> 🔒 本资料仅供校内评审使用 —— 未在 GitHub / Gitee 等平台公开发布，
>    访问需口令。请勿转载、镜像或外传。
```

**这句话直接和「开源」矛盾。任何人看到都会立刻关掉页面。**

### 重写成了什么

```
qunzhi/
├── README.md          入口，结论优先（陌生人 30 秒判断值不值得看）
├── RESULTS.md         一页看完所有结论（含 7 条不成立 + 2 条撤回）
├── LIMITATIONS.md     20 条已知边界
├── ORIGIN.md          前身是 AI 博弈游戏，怎么演化来的
├── CONTRIBUTING.md    怎么提 issue、怎么复现
├── docs/00_怎么读这个仓库.md   按身份分四条阅读路径
├── experiments/README.md       四批实验的关系 + 复算方法
└── src/README.md               代码结构
```

### 核心改写思路

**旧版开头**：「群智是一个基于多智能体的科研决策预演系统……」（功能罗列）

**新版开头**：
```markdown
> 316 次实验（140 人格消融 + 32 三臂对照 + 144 跨模型复现），
> 我们作废了 798 轮评审，承认三维人格里只有一维在两个指标上同向，
> 还发现单模型在覆盖度上名义更高。
```

**先给最反直觉的事实，再解释这是什么。**

### 教训

> **面向评委和面向陌生人，写法完全相反：**
> **评委看「创新性」，陌生人看「这对我有什么用」。**
> **开源前必须换位重写，不能直接复用参赛材料。**

```python

README 的数字  vs  RESULTS 的数字  vs  口径表的数字

# 3. 扫禁区词
"27 倍" "8.4 分" "6 个模型" "4 臂" "三批" ...
```

> **自己写的东西一定要当别人的东西来查。**

## 阶段 7：云端闸门审核

### 做了什么

用三模型对抗式审查（GLM-5.3-Flash / qwen3.8-flash / MiniMax-M2.5），
每次把仓库核心文档发给三个模型，要求它们按 JSON schema 给裁决。

**规则：任一模型给 `blocking` 或 `methodological_fix` → 打回。**

### 17 轮的过程

| 轮次 | 结果 | 修了什么 |
|---|---|---|
| 1 | 3 模型打回，**5 blocking** | 跨模型描述、三臂 4 臂、SD 矛盾、TOST、价值观 |
| 2 | 0 blocking，2 fix | 8 处 |
| 3 | MiniMax 2 blocking | TOST 醒目度、「负面结果集」夸大 |
| 4 | 0 blocking，5 fix | 三臂 A−B 补检验 |
| 5 | qwen 放行 | 7 处 |
| 6 | MiniMax 放行 | README 一个真 bug |
| 7 | GLM 提多重比较双标 | Holm 全族校正 |
| 8 | MiniMax 放行 | TOST 换真实值 |
| 9–17 | 反复小修 | 编号、口径、文件数… |

**共修 60+ 处，其中 12 个真错。**

### 重要的一个发现：**闸门也会算错**

第 17 轮 GLM 说我的 TOST 的 SD 应是 0.754。我验算三遍：

```
差值 [0,0,0,0,+1,−1,−1,−2]
Σx = −3，均值 = −0.375
Σx² = 7
SS = 7 − 9/8 = 5.875
方差 = 5.875/7 = 0.839286
SD = √0.839286 = 0.91612   ← 我的是对的
```

**GLM 用的 3.984 是它算错了。**

**处理：不因为被质疑就改正确数字。把推导逐步写进文档，让任何人可核对。**

### 闸门的三个问题

| 问题 | 怎么解决 |
|---|---|
| GLM `reasoning_effort: high` 把 token 全用在思考上，正文为空 | 降为 `low` |
| MiniMax 上下文 32K token 上限，材料太大会截断 | 材料压到 42K 字符以内 |
| 第 17 轮开始产出**错误**质疑 | **停**。移动靶，边际收益已耗尽 |

### 教训

> **对抗式审查极有价值 —— 但要知道什么时候停。**
> **三轮之内还是 0 blocking 就差不多了；开始出现错误质疑就是终点信号。**

## 阶段 9：解决推送失败（最大的坑）

### 第一次尝试：直接 push，失败

```powershell
git push -u origin master
# fatal: unable to access ...: Failed to connect to github.com:443
# after 21068 ms: Could not connect to server
```

### 诊断：为什么连不上

```powershell
# 1. 看 DNS 解析到哪个 IP
[System.Net.Dns]::GetHostAddresses("github.com")
# → 20.205.243.166

# 2. 测 TCP 443
Test-NetConnection github.com -Port 443
# → 不通

# 3. 测其他 GitHub IP
Test-NetConnection 20.27.177.113 -Port 443   # → ✓ 通，112 ms
Test-NetConnection 140.82.116.3 -Port 443    # → ✓ 通，209 ms
```

**结论：DNS 解析到的那个 IP 恰好被墙，其他 IP 都通。**

### 第一次修法：改 hosts

```
# C:\Windows\System32\drivers\etc\hosts
20.27.177.113    github.com
```

**需要管理员权限。**

### 结果：推上去了，但……

**推了一次成功后，20.27.177.113 也被封了：**
```
13:02  20.205.243.166 ✗   20.27.177.113 ✓ 112ms
14:57  20.205.243.166 ✓   20.27.177.113 ✗
```

**两个 IP 正好反过来了 —— 封锁是动态抖动的。**

### 关键发现：TCP 通了不代表能用

```python
# 只测 TCP 会误判！
20.205.243.166   TCP ✓ 114ms   →   TLS ✗ 6 秒超时
20.200.245.247   TCP ✓ 128ms   →   TLS ✗ 6 秒超时
20.233.83.145    TCP ✓         →   TLS ✓ 347ms  ← 只有这个真能用
```

**TCP 能连上，但 TLS 握手会被卡死 —— 这是 SNI 层面的阻断。**

**所以扫描必须测到 TLS 层，不是只测 TCP。**

### 最终解决：改用 SSH

#### 对比测试（各 5 次）

| 通道 | 成功率 | 说明 |
|---|---|---|
| **SSH `github.com:22`** | **5/5** | 122 ms，完全稳定 |
| SSH over 443 | 0/5 | 被封 |
| **HTTPS `github.com:443`** | **1/5** | 7451 ms，基本不可用 |

#### 为什么 SSH 不受影响

**HTTPS 走 TLS，握手的 SNI 里带 `github.com` → 被识别并阻断。**
**SSH 是纯二进制协议，没有 SNI → 不受这套拦截影响。**

#### 配置 SSH 的步骤

**① 生成密钥（无需密码短语，方便直接 push）**

```powershell
ssh-keygen -t ed25519 -C "fajstar@users.noreply.github.com" `
           -f "$env:USERPROFILE\.ssh\id_ed25519" -N ""
```

**② 复制公钥**

```powershell
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
# → ssh-ed25519 AAAAC3Nza... fajstar@users.noreply.github.com
```

**③ 加到 GitHub**

打开 https://github.com/settings/ssh/new

| 字段 | 填什么 |
|---|---|
| Title | `我的Windows电脑` |
| Key type | `Authentication Key` |
| Key | 粘贴上面那一整行 |

点 `Add SSH key`。

**④ 测试**

```powershell
ssh -T git@github.com
# → Hi fajstar! You've successfully authenticated
```

**⑤ 切换远程**

```powershell
git remote set-url origin git@github.com:fajstar/qunzhi.git
```

**⑥ 推送**

```powershell
git push -u origin master
# d4dc24d..7941e35  master -> master
# 耗时 3.98 秒
```

**对比：HTTPS 21 秒还失败；SSH 4 秒完成。**

### SSH 为何值得配

```powershell
# 实测：8 个 GitHub IP 的 22 端口
20.205.243.166   3/3  82 ms
20.200.245.247   3/3  124 ms
20.27.177.113    3/3  142 ms
20.233.83.145    3/3  156 ms
140.82.116.3     3/3  218 ms
4.208.26.197     3/3  251 ms
140.82.113.3     3/3  277 ms
140.82.114.3     3/3  616 ms
```

**全部 3/3 稳定 → 不管 DNS 给哪个 IP，SSH 都能连。**

**所以：配完 SSH，hosts 硬编码可以彻底不要了。**

### 教训

> **① 国内用 GitHub，优先 SSH，不要用 HTTPS。**
> **② hosts 硬编码治标 —— IP 会轮换，迟早失效。**
> **③ 测连通性要测到 TLS 层，TCP 通了不代表能用。**
> **④ 失败两次就停，换个方案 —— 我们在 hosts 上尝试了三四次才想到 SSH。**

## 附：常见失败与对应解法

| 现象 | 根因 | 解法 |
|---|---|---|
| `Failed to connect to github.com:443` | DNS 解析到被封 IP | **改 SSH** |
| `Could not resolve host: github.com` | DNS 或 hosts 出错 | 检查 hosts，或清 DNS 缓存 |
| `Repository not found` | 仓库还没建 | 去网页建空仓库 |
| `rejected (non-fast-forward)` | 远程有本地没有的提交 | 建仓库时别勾 README；或 `git push -f` |
| `Permission denied (publickey)` | SSH 公钥没加到 GitHub | 去 Settings → SSH keys 加 |
| TLS 6 秒超时 | SNI 阻断 | **改 SSH** |
| 中文文件名乱码 | 编码问题 | `.gitattributes` + `core.quotepath=false` |

## 附：这次配的 `.gitattributes`

```gitattributes
# 统一行尾，避免 Windows/Linux 拉下来整片 diff
* text=auto eol=lf

# 这些保持二进制
*.png binary
*.zip binary
*.pptx binary

*.md text eol=lf
*.py text eol=lf
*.json text eol=lf
```

**为什么加**：Windows 上 clone 后如果 `core.autocrlf` 设置不同，整个仓库会显示为「全部修改」。这个文件把行尾策略写死在仓库里。

## 最后：三个原则

**① 「可复算」要靠跑一遍来证明，不是靠声明。**
写完就验证，把结果贴出来。

**② 自己写的东西要当别人的东西查。**
我把自己亲手做的实验记成了「6 个模型」，实际是「3 模型 × 2 思考档」。

**③ 失败两次就换方案。**
hosts 改了三四次还是失效，才想到 SSH。**如果早点查「为什么 HTTPS 不行」，能省两小时。**
